# Seex Roadmap — 离线零部署

> 本文件只记录当前及未来工作。已完成的 0.1.x 阶段与测量结果见
> [release notes](release-notes/0.1.0b0.md#completed-01x-roadmap)；
> 不在此重复 U0–U7、V1 的执行历史。

## 目标与边界

Seex 的本阶段目标是离线、零部署的本地训练记录和图表查看，不承接已经由在线 ClickHouse 方案解决的在线事实库场景。一个本地 Native project store 应承载百万级 Run、百万级**全局去重** metric key，以及千万级实际存在的 (Run, metric key) 序列；这不是百万乘百万的全组合。主要负载同时包含大量短序列和少量长序列。

- Python SDK 只负责 Run 创建、指标上报、完成和写入诊断。移除 Python 查询、Arrow、比较、排名和依赖这些读取能力的只读 seex CLI；不以无限大的 Python 列表替代 Arrow。
- Rust Reader 与 Viewer 负责读取。Viewer 保留多个本地数据源和多 Run 曲线比较；首版图表只按 Step 对齐，每条曲线最多返回 1024 个真实点，单个面板最多同时显示 16 条曲线。
- 首版不提供全量导出、S3、按屏幕像素动态计算点数、多时间轴对齐、目标排名或研究自动化接口。Step 之外的时间戳可以继续作为上报事实保存，但不构成首版图表查询轴。
- 本地 SQLite catalog + DuckLake 是唯一首版存储组合。DuckLake 继续管理事实表和物理文件元数据；不转为 Seex 自管 Parquet 文件格式。
- 不承诺旧存储格式或旧读取 API 的兼容性。新格式必须有明确版本标记；打开旧目录应报可诊断错误，不得迁移、覆盖或误判为空目录。
- 同一目录允许多个训练进程同时写**不同** Run，同一 Run 仍只有一个写者；Reader 可并发读取。训练上报的接收与持久化仍须区分，不能把排队成功宣称为已经落盘。

## 顺序与阶段门槛

按 P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7 实施。每阶段拆成独立、可审查的小变更；功能删除、存储结构、查询优化和 Viewer 改动不得混在同一提交。普通实现项遵守仓库的五文件、约 200 行范围；本次 ROADMAP 历史清理是用户批准的单文件例外。

### P0 — 固定接口与可重复负载

- [x] 将 Python 公共面收缩到 init / log / finish / context manager / 写入诊断；删除 Api、history、Arrow、比较/排名和只读 CLI 的入口、类型桩及测试。Rust Reader 保留本地发现与图表读取，但移除首版无界全量点查询和独立 Parquet 导出入口。
- [x] 固定 Step、每曲线 1024 点、每面板 16 曲线的契约。超过限制须明确拒绝或提示缩小选择范围，不能静默放宽。
- [x] 建立可重复的小型正确性样例与大规模生成器；记录当前版本的文件数、catalog 大小、RSS、查询计划和冷/热延迟，供后续候选方案比较。

退出条件：Python 上报端到端测试和 Viewer 本地多数据源烟测通过；任何可触达的图表接口都不能返回无界点集。

### P1 — 本地存储版本与多进程写入可行性

- [x] 先用隔离样例验证 SQLite WAL + DuckLake 在多个进程写不同 Run 时的事务、快照和文件行为，再将 SQLite 设为唯一 catalog 后端并移除首版 S3 路径。
- [x] 保留 Run-writer OS 锁；对共享 catalog / DuckLake 写事务建立项目级短临界区，只串行化后台持久化和元数据提交，不阻塞训练线程的上报接收。锁等待超时与队列满必须返回可区分的错误。
- [x] 定义存储版本、首次创建、旧目录拒绝和只读打开规则；验证四个写入进程、并发 Reader、同一 Run 冲突、进程崩溃、重启恢复和完成 Run 的重试。

停止条件：若无法证明跨进程提交可恢复且 Reader 不看到不一致快照，暂停 P2–P6，先形成新的本地协调设计；不得悄悄退回单进程写入。

### P2 — 百万级目录与按需发现

- [x] 以索引化的 Run 目录、全局 metric key 字典和实际序列目录替代扫描事实表做发现；序列目录只为存在的 (Run, metric key) 建记录，不生成全组合。
- [x] Run 列表按稳定顺序做游标分页；metric key 提供精确查找和有索引的前缀检索。Reader 不一次性返回某 Project 的全部 Run，Viewer 只加载可见页、选中 Run 与选中 metric。
- [x] 为 Project、Run、key 和序列的查找验证索引计划、删除/缺失引用行为与跨数据源身份。缓存必须有容量上限，且不能复制整份百万级目录到进程内。

退出条件：百万 Run、百万全局 key、千万序列的目录发现内存不随总记录数线性增长；100 条 Run 的热分页达到最终验收目标。

### P3 — 文件布局证据与选择

- [x] 在同一负载中比较现有 (run_id, metric_key_encoded) 分区、固定数量的 Run bucket 分区、以及跨短序列共享且按 Run/key/Step 排序的文件布局；长序列允许分成有限大小的段。
- [x] 对每种候选记录目录数、稳态文件数及大小分布、DuckLake catalog 大小、单序列查询实际扫描的文件/row group、写入放大、压实耗时和峰值 RSS。以 64–256 MiB 的稳态文件作为目标区间，不以每个序列一个文件为默认策略。
- [x] 完成满足两项条件的布局选型（生产切换另行实现）：文件数主要随事实数据字节量而非序列数增长；精确 Run/key 查询可通过分区、排序统计或索引裁剪，不能扫描整个大 bucket。DuckLake 仍拥有文件清单，不增加第二套物理文件真相源。

评估与选型证据见 [P3 文件布局评估](reference/p3-file-layout.md)。选择 shared sorted 方向：短序列数量增至四倍仍为一个文件，约 84 MiB 文件上的精确查询读取 2/164 个 row group。生产布局尚未切换；探针的大批排序/合并峰值 RSS 约 4.47 GiB，后续必须验证有界写入与物理整理，不能将此选型当作 P7 内存目标已经通过。

停止条件：若候选布局无法兼顾文件数与查询裁剪，保留 P3 评估结果并重新设计索引/布局，不进入 Rollup 优化来掩盖全扫描。

### P4 — 纯追加语义与上报、查询性能

决策见 [ADR 0019](adr/0019-append-only-metric-observations.md)。不引入归档 v4 的稳定次序机制或业务压实协议。

- [x] Native v5 保留所有重复 Step 观测，删除查询与摘要的 LWW；旧格式拒绝，不迁移。同 Step 内不承诺顺序，摘要统计所有观测。
- [x] Detail 只返回视口内观测，Overview 与 Detail 共用一条 `isfinite` 过滤采样 SQL；删除视口外邻居、对齐查询 API 和查询期诊断，完整性只随 Run 生命周期。
- [ ] 修正性能探针口径，分别测入队、持久化、连接、catalog 锁、终态摘要及 flush；先定位，再单独优化，不通过扩大队列隐藏积压。
- [ ] 测完整 Reader 路径的新鲜连接、元数据、Step 窄范围扫描、Arrow 消费、原生 LTTB 与 16 曲线请求；每条曲线严格不超过 1024 个真实观测。
- [ ] 共享排序只做有界隔离探针，验证交错写入、多个长序列、RSS、临时盘与前台竞争；生产切换另立变更。DuckLake 继续拥有物理文件清单。

退出条件：重复观测、范围、摘要、重启与旧格式拒绝验收通过；性能口径可重复且资源成本明确。INCONCLUSIVE 不表示无回退。

### P5 — 分层 Rollup 与 1024 点图表查询

- [ ] 短序列直接读取有效点；长序列建立按 Step 范围组织的分层摘要，保存真实首尾与极值点。新增观测只失效并重建受影响层级；重复 Step 不覆盖历史观测。本阶段暂缓，不与纯追加切片捆绑。
- [ ] 总览和缩放查询选择最小足够层级，合并未压实尾部与必要边界点，最终每曲线严格不超过 1024 点；返回点必须对应真实观测，不能伪造聚合坐标。
- [ ] 为单序列查询设置扫描、排序、内存及取消边界。若索引或 Rollup 不可用，返回明确的未就绪/部分证据状态，不能无提示地执行无界全量查询。

退出条件：短、长、稀疏、重复 Step 和极值样例均通过；窄 Step 查询不扫描全序列，图表内存随返回点数和有限工作集增长。

### P6 — Viewer 按需读取与有界缓存

- [ ] 把数据源发现、Run 列表和 metric 选择改为分页/按需加载；虚拟化百万级列表，保留多数据源引用和 16 条曲线的比较体验。
- [ ] 保留过期请求取消，限制并发查询、结果缓存和滚动/缩放后的陈旧快照；缓存键包含数据版本，写入或压实发布后能正确失效。
- [ ] 移除像素宽度驱动的点预算和多时间轴 UI/查询分支（点预算已固定，ElapsedTime 轴入口已禁用；查询仍会返回 `ElapsedTimeUnsupported`）。单面板上限、1024 点上限和加载/错误状态在 Viewer 中可见。

退出条件：反复切换数据源、Run、metric 和缩放范围后，已取消请求不保留查询工作集，RSS 回落且旧结果不覆盖新视图。

### P7 — 规模验收与收尾

- [ ] 在 16 GB 本地 SSD 笔记本上，用固定种子生成同一目录中的百万 Run、
      百万全局 metric key 和千万实际序列：9,998,990 条 1–4 点短序列、
      1,000 条 1,024 点中等序列、10 条百万点长序列。保证每个 Run 和
      metric key 至少出现一次，并加入 1% 的旧 Step 覆写及乱序写入。
      另用四个训练进程同时写不同 Run，并在写入和恢复期间读取。
- [ ] 记录硬件、数据分布、数据/目录/文件数、catalog 大小、查询计划、冷/热延迟、各进程峰值 RSS、压实进度及故障恢复结果。每日 CI 只运行小型确定性 Acceptance；大规模负载用于里程碑验收，不作为每个提交的常规测试。
- [ ] 首版目标：Viewer 峰值 RSS ≤ 1 GiB，单写入进程峰值 RSS ≤ 512 MiB；100 条 Run 热分页 p95 ≤ 250 ms，16 条曲线热图表查询 p95 ≤ 1 s。冷查询和写入吞吐同样记录，但不以未经测量的常数掩盖其瓶颈。
- [ ] 任一目标未达成时，保留失败结果，先用计划、文件扫描统计和内存 profile 定位，再开一个独立优化候选；不得放宽 1024 点限制、隐藏不完整结果或把大量数据移到 Python 内存来通过验收。

## 执行约束

存储边界或公共 API 真正变更时，分别更新项目 AGENTS.md、原生存储说明及满足条件的 ADR；不要在本次路线图改写中夹带这些文件。日常 Acceptance 阻断相关变更，Benchmark、性能比较与 Profile 提供证据而不阻断每次提交。每阶段完成后才进入下一阶段；P1、P3 和 P7 的停止条件不能通过降低产品目标绕过。
