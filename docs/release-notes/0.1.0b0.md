# Seex 0.1.0b0

Seex 0.1.0b0 consolidates the completed PulseOn alpha/RC line, the PulseOn
0.1.1 publication, and the completed Seex 0.1.x roadmap into one beta record.
Install it with `pip install seex==0.1.0b0`, import it as `seex`, and use the
`seex` command.

This is a hard identity reset from PulseOn. Seex does not import the old Python
package, inspect `.pulseon`, read old environment variables, migrate old
catalog application tables, or restore old desktop workbench documents. Legacy
state is left untouched. The product-owned Parquet schema remains the open data
compatibility boundary when explicitly configured.

The desktop binary is `seex-app` and is distributed independently from the SDK
wheel. `seex app [PROJECT_PATH]` launches it when available on `PATH`.

## Highlights

- A Rust/PyO3 local training-metric SDK with bounded asynchronous reporting,
  explicit lifecycle and diagnostics, DuckDB or SQLite catalogs, and local or
  S3-compatible Parquet data.
- Typed discovery, metric-series queries, Arrow PyCapsule output, comparison,
  ranking, and deterministic versioned CLI JSON.
- A renderer-independent chart core and native GPUI analysis workbench for up
  to 10 Runs per View across multiple DuckDB and SQLite sources.
- Step, elapsed-time, and Viewer absolute-time presentation with explicit
  completeness evidence, last-write-wins samples, real viewport neighbors, and
  no interpolation in hover or locked cursors.
- Logical-pixel query budgets, compact immutable snapshots, bounded projection
  and path geometry, visible-track scheduling, four-way reads, and stale-result
  rejection.

## SDK and Native Storage

The native metric loop creates or opens a project-local store, under `.seex` by
default or an explicit project root. Projects and Runs have typed identities;
metric points enter a bounded in-process queue and persist through DuckLake to
partitioned Parquet data.

- Report admission is non-blocking and exposes queue-full, writer, pending,
  persisted, drain, flush, and terminal-state diagnostics.
- Creating and resuming Runs are distinct operations. One local writer owns a
  Run; terminal finish/fail and explicit flush make Parquet data visible.
- Bounded shutdown drains admitted work. Callers must stop concurrent logging
  threads before shutdown so new reports cannot indefinitely extend the drain.
- DuckDB and SQLite catalogs cover lifecycle, logging, query, aggregate,
  terminal flush, reopen, and custom local path parity.
- `data_path` may be local or S3-compatible. `catalog_path` remains local.
  Relative paths in project configuration resolve from the project root.
- Explicit SDK/CLI settings override project configuration. Credentials are
  sanitized from representations and ordinary errors.
- The catalog application schema remains backend-aware and separate from
  DuckLake internal metadata. The Parquet schema and partition layout remain
  the product compatibility boundary.

The workspace was split into model, storage, core, Python, chart, and Desktop
responsibilities with one-way dependencies. The accepted next architecture is
the performance-preserving single-crate migration described by
[ADR 0015](../adr/0015-unified-rust-sdk-performance-preserving-migration.md);
it is current roadmap work, not part of this completed release record.

## Reporting Contract

- The shipped reporting form is explicit-step numeric logging. Observation
  time is captured at admission while ingestion time remains writer-owned.
- A successful log call means the point entered the bounded process queue, not
  that it is already durable.
- Effective metric series use last-write-wins for duplicate Run/metric/step
  points. Existing non-finite evidence is retained and reported rather than
  silently repaired.
- Queue capacity and diagnostics have explicit point counts. Writer failure,
  drain timeout, flush failure, and terminal conflicts remain visible errors.

## Read, Comparison, and Ranking

The read surface starts discovery without a known Project ID and does not need
to start a writer.

- Project, Run, and metric discovery have stable ordering and bounded
  pagination. Running-Run reads see persisted points, not reports still waiting
  in another client's queue.
- Ordinary Step ranges are half-open: `[start_step, end_step)`. Reduction runs
  after last-write-wins. `max_points` is at least two; `None` or CLI `--all`
  requests the full effective series.
- Dependency-free Arrow result objects expose `__arrow_c_stream__`; PyArrow,
  pandas, and Polars are not runtime requirements.
- Native and standalone Parquet readers share typed queries. Standalone
  Parquet remains fact-only and reports missing Run metadata as incomplete
  evidence.
- Alignment supports raw Step and elapsed wall time from `Run.started_at`.
  Closed Viewer viewports may include one real neighbor on either side.
  Negative/decreasing axes and missing origins remain explicit reasons.
- Comparison reports require an explicit baseline and `minimize` or `maximize`
  direction. Raw delta is `candidate - reference`; relative delta divides by
  the absolute reference and is absent for a zero reference.
- Running and failed Runs may contribute available numeric evidence, but their
  preference stays inconclusive. Secondary metrics do not affect outcome,
  preference, rank, or tie-breaking.
- Eligible finished Runs use direction-aware competition ranking (`1, 1, 3`).
  Exact ties prefer earlier creation time, then lexical Run ID when one winner
  is required. Empty eligibility returns a successful null best result.
- CLI success and error envelopes use schema version 2 with deterministic
  kinds, ordering, reasons, pagination, non-finite encoding, and exit statuses.
  The CLI remains read-only.

LTTB remains an optional DuckDB community extension and is not bundled in the
wheel. Online installation and explicit offline loading were verified against
DuckDB 1.5.4 and LTTB 0.1.0. Offline deployments must provide a compatible
signed extension through the configured extension path; otherwise use an
unbounded query.

## Completed 0.1.x Roadmap

### Renderer-independent charting

The windowless chart crate owns series, axes, viewports, projection, ticks,
path caching, hit testing, brush selection, and zoom without depending on GPUI
or storage. It provides handle resize, selection pan, cursor-anchored zoom,
home clamping, reset, nearest-real-point hit testing, and finite visible-y range
calculation with constant-value fallback.

### Native GPUI Viewer

The first native Viewer opened an existing local DuckDB or SQLite Project on a
background worker, never constructed a writer, and kept storage work off the
GPUI thread. Independent immutable overview and detail snapshots carried
generation tags so pending or stale work could not replace current evidence.

The completed workbench expands that surface:

- Multiple retained local sources use composite source/Project/Run identities.
  A source failure does not erase another source's drawable results.
- A searchable Project/Run sidebar supports import, reveal, refresh, removal,
  pagination, Pinned and Archived placement, and per-View Run visibility
  without mutating native stores.
- Each Analysis View owns ordered Runs and Metrics, baseline, axis, viewport,
  snapshots, pending generations, errors, dock state, and persistence.
- A fixed Metric column and aligned chart tracks share one timeline. The brush,
  ruler, track pan, wheel/pinch, and keyboard zoom use one clamped viewport and
  a View-level 100 ms trailing query debounce.
- Step and absolute-time presentation, independent hover and locked cursors,
  real-sample callouts, baseline deltas, and evidence-aware drawing preserve
  source truth without interpolating values.
- The Bottom inspector exposes whole-series Summary, Ranking, and Evidence
  using the same comparison semantics as the SDK and CLI, never renderer-owned
  samples.
- The versioned `seex-workbench 1` document persists organization and
  presentation state, never metric points, credentials, connections, query
  snapshots, or geometry. Unsupported versions fail instead of being guessed.
- Zed-aligned semantic themes and compact primitives cover light/dark hierarchy,
  hover, active, selected, focus, disabled, pending, and error states.

### Resource efficiency

- Overview budgets derive from logical plot width `L` as
  `clamp(L, 256, 2_000)`; Detail uses `clamp(2L, 512, 5_000)`. Display scale,
  Run/Metric count, visibility, and organizational state do not change a
  series budget.
- A curve snapshot retains one chart series plus Run-level metadata,
  completeness, reasons, and source-row count. Hover, locked cursor, baseline
  delta, and inspector cursor index the same retained real sample.
- Render compaction preallocates from logical canvas buckets. Removed Runs and
  Metrics evict projection/path state; only visible tracks plus one viewport of
  overscan prepare geometry.
- Four reads may execute concurrently. Supersession checks run before a query
  and between Runs; stale results never enter a merged snapshot.

The full measurement record and rejected experiments remain in
[viewer-performance-validation.md](../viewer-performance-validation.md).

## Performance Record

### Reporting

On macOS 26.3 ARM64 with CPython 3.13.2, 100,000 explicit-step admissions took
0.058217666 seconds, or 1,717,691.67 calls/s, with no queue-full failure. This
measures admission only.

For 1,000 same-key reports, the release-candidate drain improved from about
24.85 seconds to 35.79 ms. Finalization remained below 40 ms and includes the
once-per-Run aggregate rebuild.

| Build | Setup median | Admission median | Drain median | Finalization median | Shutdown median |
| --- | ---: | ---: | ---: | ---: | ---: |
| Before drain work (`b7188f1`) | 0.089354 s | 0.000967 s | 24.846142 s | 0.012610 s | 0.000087 s |
| After drain work (`e971a34`) | 0.086800 s | 0.000844 s | 0.050040 s | 0.024982 s | 0.000049 s |
| Release candidate (`82df3f4`) | 0.091140 s | 0.001101 s | 0.035786 s | 0.023362 s | 0.000063 s |

### S3/MinIO reads

The opt-in MinIO query gate covered DuckDB and SQLite across 3 Runs, 4 metric
keys, and 12 Parquet files. Each backend returned 2,000 ranged points across 5
queries with zero unrelated partition reads. Read amplification was 0.922 for
DuckDB and 0.925 for SQLite.

### Viewer

- Logical budgets reduced full-Detail return points from 60,000 to 40,000
  (33.3%) and narrow Detail from 51,020 to 26,520 (48.0%).
- Compact snapshots reduced retained point storage by 90.5–92.6%. The isolated
  repeated-scale process peak fell from 1,115,308,032 to 757,563,392 bytes
  (32.1%).
- The 30-cycle isolated workload held 258,129,920 bytes warm RSS and
  267,714,560 bytes peak/final RSS, with no monotonic growth and within the
  `max(5%, 32 MiB)` final bound.
- Sharing the DuckDB database/buffer manager improved all 7 paired samples,
  with a 12.99% median improvement.
- The post-change query medians for Overview/full/narrow were
  1260.253/1267.972/515.609 ms on DuckDB and
  1267.051/1267.993/537.579 ms on SQLite, with parity, neighbors, extrema, and
  evidence checks passing.
- The final automated CPU gate's worst p95 was 2.066 ms and worst single
  operation was 2.834 ms, below the protected 8.33/16.7 ms limits.

The real multi-Metric application remains query-memory bound: one View peaked
at 5.31 GiB, the measured two-View interval peaked at 5.06 GiB, and an attached
Metal trace peaked at 7.82 GiB. These are documented hard-gate failures, not
claimed release improvements.

## Compatibility and Migration

- Python requires CPython 3.11 or newer and uses the stable ABI wheel surface.
- Pre-1.0 APIs, catalogs, and workbench documents have no compatibility
  promise. Seex intentionally provides no PulseOn import, state, environment,
  catalog, or workbench migration.
- PulseOn's move to exclusive `end_step` requires callers with formerly
  inclusive finite ranges to increase the upper bound by one. Existing
  slice-style callers should remove any compensating increment.
- Relative data/catalog paths resolve from the Project root, not the process
  working directory.
- S3 credentials require explicit configuration. Environment-variable and AWS
  credential-chain discovery remain future work.
- The product-owned Parquet schema remains the only deliberate data
  compatibility boundary across the identity reset.

## Known Limits and Remaining Gates

- DuckDB full-window/sort materialization and allocator churn dominate the real
  multi-View RSS peak. Narrow Step query separation, diagnostics caching,
  cancellation, and the 25% real RSS target are active ROADMAP U2 work.
- The final 30-cycle real workload, 280 Hz Metal gate, and macOS ARM64 release
  automation remain ROADMAP U7 work. The observed trace held about 140.57 FPS
  and a 7.11 ms HUD interval but included ten Viewer-caused two-period handlers,
  so it does not pass the strict 280 Hz criterion.
- An independent default-DuckDB reader may fail to attach or retain a stale
  snapshot while a writer is active. Use the writer client for live queries or
  open an independent reader after shutdown; the SQLite path passes.
- LTTB is optional and platform-specific. PostgreSQL catalogs, SQLite
  multi-writer parity, remote training, Web UI, MCP, arbitrary SQL/export, and
  stable 1.0 compatibility remain deferred.
