# Seex 0.1.0b1

Seex 0.1.0b1 is the second beta. Cargo package `0.1.0-beta.1`, Python package
`0.1.0b1`, and tag `v0.1.0-beta.1` identify the same source. The release keeps
the existing Parquet metric-point schema as its product compatibility boundary;
pre-1.0 stores, typed APIs, configuration documents, and machine output remain
subject to breaking change.

## Install

```console
pip install seex==0.1.0b1
cargo add seex@0.1.0-beta.1
```

The GitHub prerelease also contains `seex-app-macos-aarch64` and its
`seex-app-macos-aarch64.sha256` checksum. This unsigned Viewer is independent
from the Python wheel. After verifying the checksum, install it as `seex-app`
on `PATH`; `seex app [project-path]` then launches it.

## Highlights

### One Rust and Python model

- The publishable `seex` crate provides typed Run creation/resume, atomic
  metric logging, lifecycle transitions, Reader queries, comparisons, and
  rankings. Desktop, PyO3, and the public Rust SDK share this implementation.
- Python `Run`, `Api`, `Settings`, and `MetricSeries` expose the same storage
  and evidence model. `MetricSeries` streams the existing six-column schema
  through the Arrow PyCapsule protocol without requiring PyArrow.
- Explicit step, relative-time, and timestamp ranges are typed. Callers choose
  strict bounded point limits or explicitly request a full series.

### Reader, CLI, and storage

- Reader screen queries use bounded extrema with closed-viewport neighbors;
  full queries preserve last-write-wins effective points. DuckDB LTTB remains
  an opt-in native storage dependency for the separate long-series query path.
- The read-only CLI supports stable JSON schema version 2 for Projects, Runs,
  metrics, comparisons, autoresearch leaderboards, and best-Run selection.
- DuckDB and SQLite catalogs share the local and S3-compatible Parquet product
  boundary. Configuration supports explicit catalog/data paths and redacted S3
  credentials; owner-only global credential files remain required.

### Desktop Viewer

- The GPUI Viewer reads native stores directly and keeps overview/detail reads
  bounded independently. Multi-Source workbenches retain source-qualified Run
  identity, unavailable references, view layout, expanded Projects, and
  background autosave state.
- Sources can be added, managed, reloaded, archived, exported, and imported.
  Workbench import preflights alias rewrites and allowlist additions, flushes
  current autosave state, and commits configuration plus Workbench atomically.
- Stale reloads and read generations cannot replace newer state. Cancelled or
  inactive reads retain no snapshot, and Inspector actions cannot bypass the
  no-Source disabled state.

## Packaging and release boundary

- `seex` is the only crates.io package. `seex-python`, `seex-app`, and
  `seex-plot` stay private; the standalone crate package contains no workspace
  path dependencies or private source.
- Release tags pass correctness, package, wheel/sdist, catalog parity, MinIO,
  bounded Reader, LTTB, and Viewer gates. crates.io publication completes
  before PyPI publication.
- Python distributions and the macOS Viewer use separate artifact channels and
  attestations. Desktop files cannot enter the PyPI publish glob; the Viewer
  and checksum are attached only to the GitHub prerelease.

## Correctness fixes since 0.1.0b0

- Configuration saves stage only modified owner documents and preserve an
  existing relative Source path when only its Project allowlist changes.
- Workbench import keeps its modal protection until flush and disk transaction
  completion; unrelated unavailable Sources no longer block valid mappings.
- Expanded-only missing Projects appear as unavailable and recover without
  losing expansion state. Older reload results and no-Source Inspector
  shortcuts are ignored.

## Known limitations

- The default DuckDB catalog cannot guarantee an independent reader can attach
  while a writer is active. Open `Api` after Run finalization for portable
  behavior across catalog backends.
- The first Viewer artifact targets macOS ARM64 and is unsigned. Python wheels
  do not contain a desktop executable.
- Compatibility and migrations for typed APIs, CLI JSON, catalog application
  tables, and configuration documents are not frozen until the future 1.0
  contract. Legacy `.pulseon` stores are neither discovered nor migrated.
